## 实际长等待发生在响应开始前

最慢请求可关联到 CC UTC 03:17:09.767 的主线程 api-request：

| 阶段 | 现场日志 |
| --- | --- |
| WS 请求 | 03:17:09.785，复用连接 32，使用 continuation，仅发送 3 个增量 input items |
| 等待失败 | 03:19:09.797，first_event 阶段 Timeout，耗时约 120 秒 |
| SSE 回退 | 03:19:09.803 开始；03:19:23.102 返回 HTTP 200 headers |
| 模型输出 | 03:19:23.553 首事件，03:19:28 左右完成 |

记录的总耗时 138.563 秒，首事件 133.946 秒，最大事件间隔仅 1.873 秒。CC 最终得到 Bash 调用，记录的输出 usage 为 236 tokens。这次不是 138 秒都在生成长工具参数；主要时间发生在 WS 无首事件和随后 SSE 等待响应头。

同一连接在上一请求完成约 40 ms 后就被再次使用，不能认定是长时间闲置失效，也没有证据断言 VPN、代理或上游哪个环节造成未确认请求。准确网络根因仍未定位。

社区的 [Codex #23807](https://github.com/openai/codex/issues/23807)（Open，报告 0.132.0 / Windows）和 [#42914](https://github.com/openai/codex/issues/42914)（Open，报告 0.153.4 / Linux）也描述了已建立 WS 在被动读超时前长时间等待的现象。它们是同类风险的交叉证据，不证明与本次故障具有相同网络根因；本轮没有复制其实现或同步上游 checkout。

## 已实现的改动

### 启动预算与生成空闲时间分开

ChatGPT Messages 的 WS 路径新增默认 **30 秒**启动总预算，覆盖连接检出后发送请求和等待首个可开始下游响应的事件。ping/pong 或持续的 prelude 元数据不会重置这份总预算。收到 response.created 等响应事件后，启动预算结束，后续生成继续使用原有 idle timeout。

30 秒是根据本窗口正常 WS 首事件最大约 12.4 秒选择的保守默认值，不保证覆盖所有真实负载。可选 `chatgpt.websocket_startup_timeout_seconds` 必须为正，未配置时自动使用 30；无需用户为了获得保护手工填写。它不是包含握手、HTTP 回退和模型生成的端到端 SLA。

Auto 继续使用原有输出前 SSE fallback：清理失败连接的 continuation，并以完整原始 input 恢复，不把只属于 WS 的 previous_response_id 发到 HTTP。没有增加重连轮次、周期性 WS 恢复或输出后的透明重放。首事件前失败仍不能保证上游从未开始计算，因而不声称 exactly-once 推理或只计费一次。

原生 `/v1/responses` 当前走直接 HTTP/SSE，不经过这段 WS 启动逻辑。此前假设它也会走 WS 的冒烟预期已按实际调用链纠正；其直接 SSE 对照保留，未将它冒记为 WS 恢复验证。

### 启动元数据缓冲有界

源码还发现 prelude 使用无界 Vec，之后在消费者尚未启动时逐条发送到容量 1600 的 channel。夹具发送 1601 条元数据后再发送合法响应，修改前稳定超过 2 秒测试上限，无法进入消费阶段；这不是本次生产 120 秒等待的已确认根因。

新增 64 个事件和序列化累计 256 KiB 的启动元数据边界，超过边界在输出前按已有 Auto 策略恢复；这不是精确的物理堆内存计量。合法边界内的元数据仍保留，恰好 64 条后跟正常响应的正向测试也通过。不靠扩大 channel 或内存掩盖消费者启动顺序问题。

### continuation 诊断

本窗口有 29 次 body_mismatch、27 次 connection_not_reused、11 次 busy、11 次 missing_session、2 次 prefix_mismatch。主线程可见 request shape 只有两种、params 一种；部分不匹配前有 non-stream 请求，但时间邻近不足以证明是辅助调用污染了主会话。

本轮没有放宽 canonical body 匹配。continuation decision 新增 request_id，body_mismatch 记录变更的顶层字段名；最多 16 个字段、每个最多 64 个字符，不记录字段值、提示词、工具定义或账号身份。启动失败同时记录阶段、连接复用、连接 ID、耗时、预算和 prelude 大小，便于下一窗口定位问题。

## 其他观测

CC 有 13 个工具结果标记为 error：11 个 Bash 非零退出，2 个 Read 的文件不存在。它们处于工具执行层，与代理 HTTP/stream 错误分开；本轮不通过改写命令、文件路径或工具结果来隐藏错误。另一条约 78 秒的请求在约 1.4 秒收到首事件，之后持续生成，与上面的启动等待是不同情况。

## 验证

- 修改前先复现 1601 条启动元数据导致的 channel 阻塞；修改后能恢复 SSE，断言增量 WS 只发最后一项，而恢复 HTTP 保留完整 input 且不带 previous_response_id。
- 静默连接、持续 ping、持续元数据三组均受独立启动预算约束。超量事件和超大元数据都恢复；合法 64 条边界仍成功。
- 启动预算设为 1 秒、response.created 后生成停顿 1.2 秒仍完成，没有触发 HTTP 重放，验证预算只覆盖启动。
- `cargo test --locked --workspace --all-targets --quiet`：675 项通过；workspace Clippy（warnings denied）、格式及 diff 检查通过。
- 候选 debug CLI SHA-256：`f001aeb59bdab7a2673b570fd221104f61bb232911283e9b582fd81cdde5a7b2`。
