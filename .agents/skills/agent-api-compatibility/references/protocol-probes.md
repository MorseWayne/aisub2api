# 受控客户端与协议实验

在需要确认实际发送条件、恢复行为、端到端转换或日志/指标时读取。已有失败样本足够时先用小范围单元/集成测试，不为每项修改启动完整工具链。

## 分开验证层次

| 层次 | 能证明什么 | 不能直接证明什么 |
| --- | --- | --- |
| 转换器/状态机回归 | 字段、identity、事件类型和边界转换 | 客户端会否发这种形状、实际可达性 |
| 真实客户端＋模拟上游/MCP | 实际请求形状、工具执行、重试、错误恢复 | 真实模型理解、私有 backend 接受度、缓存收益 |
| 获准的真实上游 | 当前账号、模型及调用路径的实际表现 | 其他账号/版本的能力或普遍性能结论 |

本地 fixture 决定模型响应时，应在结论中注明。模型按 fixture 调用成功不等于真实模型能理解 opaque 引用或工具提示。

## 隔离实验环境

使用任务独立的临时目录、回环端口、虚构客户端/上游凭据和合成文件。按目标工具支持的配置变量隔离状态，例如 `CLAUDE_CONFIG_DIR`、XDG config/cache 目录；不要改写现有个人配置或复用系统环境变量作脚本内部变量。

客户端子进程只继承必要环境；显式指定模拟端点，关闭不必要流量与自动更新，检查凭据来源。环境参数不足以证明任意程序完全断网；若这是验收条件，使用实际网络隔离。

运行前检查固定版本的 `--help`。不要把一次实验的 CLI flags 当永久契约：

- Claude Code 的 bare 模式适合普通协议探测，但本会话的 2.1.318 在该模式下未注册 ToolSearch。
- 测 MCP 时使用显式配置和工具权限，检查服务器已连接、实际 tools 列表、是否真的有 deferred 字段；不要仅凭环境开关宣称已测工具搜索。
- 把模型推理仅指向模拟接口；显式注入的 MCP fixture 只处理合成数据，不执行无关命令。

给子进程、HTTP 请求、服务启动和单次案例设置有界超时。记录退出码并清理本次启动的进程；超时表示在观察窗口内未完成，不能描述成“永远无法恢复”。

## 选择与变更匹配的场景

### 请求和工具

- 同时观察客户端→代理和代理→上游；路由别名、协议头、JSON 字段、effort、schema 和日志分别比较。
- 普通对话、工具调用、分段参数、tool result 回传，必要时加入 thinking→tool→尾随文本。
- ToolSearch 的初始请求、引用结果、发现后 schema、目标 MCP 调用；不支持时的显式降级。
- 未知 typed 内容可以保留或明确拒绝；不可静默删除带 canonical call identity 的整个结果。
- 测会话/缓存时区分 conversation、device/account 和 provider runtime identity；明确变化前后哪些 identity 应保持稳定。

### 错误与恢复

- 至少同时考虑原始字段校验错误与带名称的 capability/beta 拒绝。已知 token 在错误 envelope 下仍能触发恢复，可能掩盖状态码被改坏的问题。
- 用 relay 或等效观测记录客户端实际收到的 HTTP 状态和错误消息；不能只记录上游返回了什么。
- HTTP 422 校验错误变成 502 会改变 SDK 重试/客户端恢复语义。错误消息前缀和 type 也可能参与匹配。
- 测失败后成功的场景时，不让 fixture 在请求形状仍错误时无条件放行，否则会把“重试了一次”误判成“正确降级”。

### 流式生命周期

- 区分协议成功终结、原生错误终结、正常 HTTP EOF 和传输错误。`message_stop`、Responses terminal、Chat Completions finish/[DONE] 各依其契约处理。
- 测普通文本、thinking、工具调用的截断；不能只给 tool-use 设置保护。
- 已开始 SSE 时 HTTP 200 仍可包含失败，检查错误事件和指标，不仅检查状态码。
- 验证无成功终结时不会补造 `stop`/`completed`，同时验证完整终结后的连接关闭、无空行尾帧和结束后仍保持连接不会误报或拖住请求。
- 保留正常原生错误内容，不为了完成边界检查制造第二个“缺少 message_stop”错误。不要无意声称已验证所有字段和 block 生命周期。

## 记录与判断

为需要复核的实验保存客户端/上游版本与摘要、配置的非敏感部分、案例名、转换前后请求、实际状态/事件、退出码及断言结果。敏感请求、第三方模块与完整日志保留在约定的本地目录，提交时只纳入必要的脱敏 fixture。

将恢复后的成功请求与失败尝试区分记录。日志应标明输入/推导/最终发送值各自的层次；输入 effort 与模型 capability clamp 后的发送值不同，不一定是错误。

如需 HAR 供 REA 检查，保留真实观察到的请求/响应；标注模拟响应、时间或端口归一化和敏感值移除。历史 HAR 不证明生产归属、时序因果或部署真实性。

修改前后对照应回答：失败是否复现、协议/配置是否改变、是否恢复、失败是否仍可见。成本、延迟或缓存主张另设基线、实际调用路径、样本和预算。
