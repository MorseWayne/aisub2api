# Agent API 适配优化

以用户实际调用的问题确定范围，把官方契约、客户端行为、社区经验和目标工具的真实请求路径交叉验证，交付最小、可复现、可回归的改进。逆向与同类实现都只是证据来源，不是默认的第一步。

## 选择需要的参考

- 要比较 issue、修复 PR 或同类代理，读 [community-evidence.md](references/community-evidence.md)。这通常应与客户端分析并行推进，不能最后才补。
- 要运行真实客户端、本地模型/MCP fixture 或验证 SSE、错误降级，读 [protocol-probes.md](references/protocol-probes.md)。
- 需要 REA、原生发布产物或 Bun 模块分析时，读 [client-artifacts.md](references/client-artifacts.md)。已有源码、协议或最小复现足够时跳过逆向。
- 目标为 aisub2api 时，读 [aisub2api.md](references/aisub2api.md) 定位入口和已有证据。其他仓库不加载这份项目上下文。

按任务选择参考，不默认加载全部文件。

## 从问题和边界开始

先确定客户端与版本、下游协议、provider 与上游协议、实际故障或验收目标，以及已有用户改动。沿目标仓库的指引，检查相关 handler、路由、转换器、错误映射和测试；已知路径和 symbol 优先直接读取及 `rg`，代码图谱按复杂度选用，不设前置门槛。

区别三个契约：客户端期望的行为、代理公开支持的子集、具体 provider/账号实际允许的行为。模型出现在目录中，不证明它支持所有端点或工具能力。

涉及状态时确认其 identity 和所有权：

- 客户端 conversation/session、provider 运行时 session、账号/device identity 各自的作用域。
- 模型别名、上游 model ID、provider/account 与请求协商字段是否影响请求 identity。
- prompt cache key 与 continuation identity 的区别；加密内容或 thinking signature 的签发/使用边界。

不根据 token 外形推断跨账号或跨 provider 可复用，不用 device/user identity 替代 conversation identity。

## 建立证据并确定优先级

优先处理真实用户故障、生产请求、明确验收和可复现的社区失败场景。按影响程度、出现频率、适用版本及复现可信度排序；stars 数、代码已经存在和未来可能用到不构成需求。

组合使用需要的来源：

- 官方协议、SDK 和网关文档：字段、错误与生命周期约束。
- 客户端源码、发布产物与真实客户端记录：发送条件、能力门控、恢复分支。
- 同类项目的 issue、当前 PR diff、测试和发布记录：真实场景、方案、边界与代价。
- 目标工具的源码、真实调用链和受控复现：确认是否存在同一问题。

联网核验当前文档、社区状态与版本，不把过期记忆或搜索摘要当结论。记录 commit 或产物摘要；同一个 package version 不保证字节相同。

为复杂任务维护紧凑的对照表：

| 证据与版本 | 触发条件/协议变化 | 本项目入口与行为 | 分类 | 最小动作 | 验证与局限 |
| --- | --- | --- | --- | --- | --- |

分类使用“已覆盖”“已复现需修复”“待验证”“不适用”。区分已观察事实、源码推断和待验证假设。静态命中、AST 节点和 issue 状态都不能单独证明实际运行行为。

## 复现与最小修复

先裁剪故障到请求字段、事件顺序或一段真实调用链，再补能体现外部契约的回归；若本项目已经通过，就保留有价值的回归，不为“优化”再加一套实现。

常见复现需要覆盖转换前后两侧，而不只检查 HTTP 200：

- 字段/协商头是否配套，未知 native 字段是否无意丢失。
- tool call/result identity、工具 schema 到达时机、分段参数和 block 类型是否一致。
- 成功终结、错误终结、正常 EOF、传输错误及客户端恢复是否被正确区分。
- 原始输入设置、实际上游参数、日志和指标是否在同一层语义下相符。

以 cut-first 方式选改动：修复当前证据支持的最小路径，复用已有转换/校验边界。新增字段、缓存、回退、状态机或抽象要有当前调用方和验收标准；不复制整个客户端调度器，也不把不同版本的社区 workaround 叠成默认行为。

性能优化先明确实际查询/调用路径和预算。测试通过、payload 变小或本地 fixture 成功，都不直接等于缓存命中、token 费用下降、模型质量或生产吞吐提高。

## 验证与交付

先验证变更层，再覆盖实际受影响的调用路径。涉及核心协议或共用转换器时检查相关调用方、下游编码与已有回归；检查通过后，仅因新改动、失败或未解决的风险扩大测试，不反复跑无关检查。

真实客户端可以接本地模拟模型服务与 MCP fixture；真实模型、真实 OAuth backend 和付费能力是另一种验证范围。复用用户已有授权，缺少真实上游授权或预算时继续静态和本地工作，不把整项任务停在这里。

沿用仓库的交付格式，说明改了什么、为什么、影响边界、复现前后、已验证结果和未覆盖项。多来源审查可保存带来源链接的报告；简单修复不强制创建一套文档。将历史证据标注版本，当前设计只描述有效行为。

不自动强制同步参考 checkout，不把使用本 skill 当作 commit、push、部署、重启现有服务或联系社区维护者的授权。报告实际完成程度，保留用户已有改动。
